What this page is for

POC 1 loaded batches of files. POC A makes the data live: a simulator changes a real database every 5 minutes, and Google Cloud services carry each change into BigQuery within minutes. This page defines every table that path reads or writes, so each developer can build their part against one agreed schema.

Required values and checks

  • G2: only the primary key and updated_at are NOT NULL, as in the POC 1 stage tables. Id formats are CHECK constraints. Nothing else is enforced, so the simulator can plant bad data.
  • Allowed values (priority, severity, event type…) stay dbt accepted_values tests. The plan moves only the type and format rules to the source (task C7).
  • Warehouse: a column is NOT NULL only when its value is always known, as in POC 1. Keys are declared NOT ENFORCED and tested by dbt.

Lineage columns

On every published warehouse table (plan 4.6). They replace POC 1's _run_id and _loaded_at. Exceptions: the native materialized views and map_tenant_access, which hold only what their query selects; on dim_date, _source_system is generated.

Tenant column

Every published table has tenant_id: the CRM account id of the store's top-level account (D-23). The exceptions are dim_alert_type, status and dim_date. Facts take it from the store; dim_account takes it from its own hierarchy.

tenant_id is NULL for an internal-only store, one with no CRM record (DQ37), such as the probe store S999. Row access policies hide those rows from every tenant; internal users still see them.

How the ids stay consistent across sources

  1. Every source starts from the same POC 1 clean batch, frozen in task 0.3.
  2. specs.md (task 0.7) fixes which stores belong to which CRM account, and which 2 stores have none.
  3. The simulator reads the current store, device and wheel lists at the start of every run instead of keeping a copy, so a moved device or a closed store is never used afterwards.
  4. Planted unknown ids are drawn from ids that are never seeded and never used by the probe (decision 1).
  5. The CRM’s g2_store_id and g2_device_id hold G2 ids exactly, so the tenant path joins on equal values; a broken link is flagged (DQ37, DQ45–DQ47), never guessed.

Column renames Proposed

The plan leaves the column mapping to specs.md. This page applies four rules, so the mapping is predictable:

  1. A bare column takes its entity's prefix: id → store_id, name → store_name, type → device_type.
  2. A reference column becomes <entity>_id (plan 4.6): fk_store → store_id, alert_type → alert_type_id.
  3. fk_date becomes the partition column the plan names: alert_date, event_date. The history's changed_date becomes event_time to match.
  4. Everything else keeps its POC 1 name, so parity (task C4) compares like with like.

The plan's parity example in C4 uses opened_at and priority; with these rules they are alert_time and priority_name. The rules apply to the ported POC 1 tables only: tables new in Phase 2 keep their source’s names (status, event_ts), as the plan does for dim_account.

Columns that go

  • _run_id, _loaded_at: replaced by the lineage columns.
  • fk_assigned_to, fk_changed_by: become assignee_token and changed_by_token. Personal data never reaches the warehouse (D-29).
  • is_valid, invalid_reason Proposed: a future time (DQ34) or an end before the start (DQ38) is now a critical check. The row is quarantined to dq_{env}.quarantine_alert and never reaches the fact.
  • Tables dim_brand, dim_user, dim_team: folded into dim_store, or replaced by tokens and a team name on the facts.
  • Mart columns holding a person: next_step_owner, issue_owner become tokens Proposed (P9).

The POC B schema doc, integrated

POC_B_Proposed_Scema.html describes the CRM entities, their relationships, the cross-POC links and the tenant rules. Everything in it is now on this page. This section records what was taken as is, what was corrected against the plan, and what its open points became.

Taken as is

  • The three CRM entities, their keys and links: account.csv, store.csv, work_order.csv.
  • The tenant path: G2 store → Active CRM store → account → top-level account = tenant_id (int_store__tenant).
  • Unmapped store: tenant_id NULL, is_customer_store false, DQ37. A vendor’s store keeps a tenant but isn’t a customer store.
  • Customer = enum CUSTOMER and status Active; an unknown code is UNKNOWN (DQ36).
  • The published outputs dim_account, dim_store, fct_work_order, and the link to map_tenant_access (POC D).
  • Its provenance labels: this page’s Proposed marks the same “Derived” and “Proposed / TBD” items.

Corrected against the plan

  • raw_g2.stores.store_id and raw_g2.device_locations.device_id are raw_g2.g2_stores and raw_g2.g2_device_locations, change logs with one row per change. dbt reads the current rows from stg_g2__stores and stg_g2__device_locations.
  • “Confirm the exact key name” for the work order’s device: plan 4.3 names it g2_device_id.
  • raw_crm.load_log was marked Proposed / TBD: it is in plan 4.2 and task B3, so it is defined (columns beyond the plan’s are marked).
  • Added what the doc leaves out: manifest.json, the stg_crm__* views, the map_customer_type seed, the contact columns and their token, and the snapshot (B10).
  • The doc names dim_store as POC C2’s model enriched by B7; here it is one card, with the tenant columns from int_store__tenant.
