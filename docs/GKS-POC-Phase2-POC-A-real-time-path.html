Executive summary

1.1Purpose

POC A makes the warehouse follow the source as it changes, instead of waiting for the next batch of files.

It captures every insert, update and delete in the simulated StorePort G2 database (Cloud SQL PostgreSQL) with Datastream, and writes them as an append-only change log in BigQuery. It streams loss-prevention (LPOS) case events through Pub/Sub straight into BigQuery. It adds a stand-in for the client's existing g2_datalake. dbt then turns the change log back into one current row per record, keeps deleted records as flagged rows, and keeps the alert facts current with incremental merges that give the same answer as a full rebuild.

POC A also builds the source simulator that keeps every source changing all day. POCs B, C, D, E and F all build on the data it produces.

1.2Business problem

POC 1 answers the question "Is this store protected right now? If not, why, and who fixes it?" from batches of files. That answer has limits:

  • It is stale. The store colour is only as fresh as the last batch, often hours old.
  • Deletes vanish. When an incident is deleted at the source it is missing from the next file, and nobody can tell "deleted" from "lost".
  • Order isn't guaranteed. With continuous changes, an older change can arrive after a newer one. Applied blindly, it would overwrite the newer state.
  • Full reloads are wasteful. Rebuilding every table on every run costs time and money as data grows.
  • Silence is ambiguous. With batches there is no way to tell "nothing happened" from "the pipeline is broken".

POC A replaces the batch path with change data capture and streaming, so the warehouse sees each change within minutes, keeps all of them, applies them in the right order and raises an alert when changes stop arriving.

1.3Expected outcome

At the end of POC A (Gate G7, Day 10):

  1. Cloud SQL poc-ops-db runs the G2 schema (11 tables) with logical decoding on. It is seeded from the frozen POC 1 batch plus the probe store S999 and device D999.
  2. Datastream poc-cdc-stream copies every insert, update and delete into raw_g2, append-only, after a full backfill. A frozen copy of the first load sits in raw_g2_parity.
  3. One stg_g2__<table> view per table gives one current row per key, with deleted keys flagged.
  4. The first copy is proven complete: key counts in Cloud SQL equal non-deleted keys in staging for all 11 tables (AT-15).
  5. Case events flow Pub/Sub → BigQuery subscription → raw_lpos.case_event within 5 minutes. Planted duplicates are visible. A message BigQuery can't write ends up in the dead-letter subscription (AT-22, AT-23).
  6. The simulator runs as a Cloud Run job every 5 minutes and changes every source. Its heartbeat proves the whole path is alive.
  7. sim_g2_datalake holds wheels and wheel events, and an hourly scheduled query writes derived alerts.
  8. fct_alert and fct_alert_history are incremental, keep deletes, respect the order of changes and equal a full rebuild after three scripted change batches (AT-17, AT-18).
  9. A change in the database reaches fct_alert and mv_store_health within 20 minutes, five times out of five (AT-16).

1.4POC A in simple terms

POC 1 is a morning newspaper. POC A is live news.

  • The source database already keeps a diary of every change it makes (the write-ahead log).
  • Datastream reads that diary and writes each entry as a new row in BigQuery. Nothing is ever overwritten.
  • dbt reads the whole diary and works out what each record looks like now. A deleted record stays, marked "deleted".
  • The alert tables take in only what changed, every 15 minutes, and a nightly full rebuild checks they are still right.
  • Case events are messages. Each one is written straight into BigQuery as it arrives.
  • A simulator plays the client's systems, so there is always something changing to react to.
  • A heartbeat row travels the whole path every 5 minutes. If it stops arriving, an alert fires.

2.3Business rules

  1. Every insert, update and delete in the G2 database is captured. None is lost.
  2. raw_g2 is append-only. Nothing in it is updated or deleted (D-25).
  3. The current state of a record is its newest change, ordered by source time, then by sequence number.
  4. Deletes are soft. A deleted record keeps its last full version with is_deleted = true and deleted_at.
  5. An older change never replaces a newer row in a fact.
  6. A database change reaches store health within 20 minutes. A case event can be queried in raw_lpos within 5 minutes.
  7. Duplicate case events are kept in raw and counted once downstream (deduplicated on event_id).
  8. A message BigQuery can't write goes to the dead-letter topic. It is never silently dropped.
  9. The incremental facts must equal a full rebuild. Any difference is an error to explain (DQ39).
  10. The probe store S999 has no CRM record, so it is internal-only and no tenant ever sees it.
  11. If the simulator, the database or the stream stops, an alert fires within 15 minutes.

Source-data rules
  • Every G2 table has a primary key and updated_at TIMESTAMPTZ NOT NULL DEFAULT now(), kept current by a trigger on each UPDATE (0.5).
  • There are no foreign keys, so the simulator can plant an unknown device or store (DQ33).
  • Store ids match ^S\d{3}$ and device ids ^D\d{3}$. The probe is S999/D999; planted unknown ids are never seeded and are never S999 or D999 Schema · decision 1
  • Case events must match the Avro schema at publish time. A message that doesn't is refused by the topic and never stored.
  • About 2% of case events are duplicates (same event_id, new message id) and about 1% name an unknown store.
  • About 0.5% of wheel events name a wheel that doesn't exist (DQ43).

Data moves through five layers. Each layer has one writer and one job.

6.1Source layer: schema g2 in Cloud SQL

  • The 9 POC 1 stage tables with the same columns, but real types instead of text, a primary key and updated_at. Two new tables: store_access and heartbeat. Plan
  • updated_at is set by a trigger on every UPDATE, so the simulator never has to remember it.
  • No foreign keys and no cross-column checks, so defects can be planted on purpose.
  • PostgreSQL now enforces types and formats. The POC 1 rules BAD_TYPE and BAD_PATTERN are marked "enforced at source" in C7.

6.2Raw layer

Change data capture

Tasks A1, A2, A4, A5 · Dev 2

7.1How it works

  1. PostgreSQL writes every change to its write-ahead log (WAL). With cloudsql.logical_decoding = on, the WAL also carries enough to decode row changes.
  2. The publication poc_pub names the 11 tables whose changes are shared.
  3. The replication slot poc_slot (plugin pgoutput) remembers how far Datastream has read, and keeps WAL until it has.
  4. Datastream first backfills each table (a full copy), then reads new changes from the slot.
  5. In append-only mode it writes one BigQuery row per change into raw_g2.g2_<table>.

7.2Cloud SQL instance (A1)

  • cloudsql.logical_decoding = on. Public IP, SSL required. Authorised networks: Datastream's static IPs for us-central1.
  • Backups off and deletion_protection = false: it's a sandbox.
  • lifecycle { ignore_changes = [settings[0].activation_policy] }, because night-off (E8) stops and starts the instance.
  • Passwords from random_password, stored in Secret Manager as poc-ops-db-datastream and poc-ops-db-simulator.

13.3Failure handling principles

  1. Never overwrite raw. raw_g2 and raw_lpos only grow, so any state can be rebuilt.
  2. Never lose a delete. Deleted records stay as flagged rows in staging and facts.
  3. Never let an older change win. The fact merge drops a change older than the row it holds.
  4. Never drop a message silently. Unwritable case events go to the dead-letter subscription.
  5. Keep duplicates where they arrive, remove them once. Raw keeps them; staging deduplicates and counts them.
  6. Quarantine, don't delete. Critical rule failures go to dq_{env}.quarantine_alert with the reason.
  7. Catch what increments miss. The daily full rebuild compares with the incremental facts (DQ39).
  8. Protect the source. Never leave the stream paused with the database and simulator running for more than an hour.
  9. Make silence loud. A stopped simulator, database or stream raises an alert within 15 minutes.

Final understanding

POC A turns a warehouse that reads files into one that follows its sources.

The simulator keeps a stand-in G2 database, a case-event stream and a lake changing all day. Datastream copies every database change into an append-only log, and Pub/Sub writes every case event straight into BigQuery. dbt reads the log and rebuilds the current state of each record, keeping deletes as flags, so late or out-of-order changes still land correctly. The alert facts take in only what changed, never let an older change win, and are checked against a full rebuild every night.

A heartbeat travels the whole path every five minutes, so silence is always noticed, and a probe proves that a change reaches store health within 20 minutes.

simulator→ Cloud SQL→ Datastream→ raw_g2→ stg_g2__*→ fct_alert*→ wh_dev → store health
simulator→ Pub/Sub→ raw_lpos· simulator→ sim_g2_datalake

The outputs support the rest of Phase 2:

  • POC B matches G2 stores from stg_g2__stores, and its CRM export runs inside the simulator.
  • POC C builds its dimensions, parity, validation and story tables on POC A's landing data.
  • POC D gets its access table from store_access through CDC, and tests access removal through the source.
  • POC E schedules, publishes and watches it all.
  • POC F scales the alert facts for the benchmark.
The central principle

Every change at the source reaches the warehouse, in order, and nothing is lost: raw keeps every change, deletes become flags, late changes still land, and an older change never overwrites a newer one.
